# التحديث الهوائي (EAS Update)

`expo-updates` كان منصّباً من زمان بس بدون إعداد، يعني ما چان يشتغل: أي تصليح
مهما چان صغير چان يحتاج بناء جديد ورفعه للستور وانتظار المراجعة. الآن `app.json`
بيه `updates.url` و`runtimeVersion`، فالتحديثات صارت تنشر بأمر واحد.

## النشر

```bash
npx eas update --branch production --message "وصف التغيير"
```

القنوات معرّفة أصلاً بـ `eas.json`: `development` و`preview` و`production`.
البناء ياخذ قناته وقت البناء، والـ branch ينربط بالقناة من لوحة Expo.

## أي بناء يستلم التحديث؟

`runtimeVersion.policy = "appVersion"`، يعني التحديث يوصل **فقط** للبناءات اللي
بنفس `version` بـ `app.json`. تحديث منشور والـ version 8.1.0 ما يوصل لبناء 8.0.0
أبداً.

اخترنا `appVersion` مو `fingerprint` لسبب محدد بهذا الريبو: `app.config.js`
يشيل بلگنات Firebase إذا ملفات `google-services.json` / `GoogleService-Info.plist`
مو موجودة محلياً (وهي gitignored). مع سياسة `fingerprint` هذا يعني أن النشر من
نسخة نظيفة يحسب بصمة مختلفة عن بصمة بناء EAS، فالتحديث ما يوصل لأي جهاز وبدون
أي رسالة خطأ.

## القاعدة الوحيدة اللي لازم تنحفظ

**أي تغيير نيتف = بناء جديد + رفع `version`.** إضافة مكتبة إلها كود نيتف، أو
تغيير بلگن، أو ترقية SDK — كلها ما تنشر بـ OTA. إذا انرسل جافاسكربت يستدعي
موديول نيتف مو موجود بالبناء، التطبيق يفشل عند الإقلاع.

الجافاسكربت والصور والترجمات و`i18n/*.json` كلها تنشر بـ OTA بلا مشكلة.

## متى يشوفه المستخدم؟

`fallbackToCacheTimeout: 0` — التطبيق ما ينتظر التحديث عند الإقلاع (ما يتأخر
الفتح). ينزّل التحديث بالخلفية ويشتغل بالتشغيل **اللي بعده**. يعني كل تحديث
يوصل بفتحتين، وهذا مقصود: انتظار الشبكة قبل الشاشة الأولى أسوأ من تأخير فتحة.

## علاقته ببوابة التحديث الإجباري

مختلفان تماماً. `AppUpdateGate` يقارن نسخة التطبيق بـ `GET /config` ويطلب من
المستخدم يروح للمتجر — هذا للبناءات النيتف. الـ OTA ما يمرّ بيه أبداً ولا يغيّر
`version`.
